# 腾讯云文档元素格式规范

> 来源：腾讯云产品文档写作规范体系 TAPD Wiki 官方规范（代码规范、链接规范、举例规范、步骤规范、表格规范、图形规范、视频规范、界面控件规范、项目列表规范、内容引用规范、说明与注意规范）

---

## 一、代码规范

文档中代码包括如下类型：
- **代码片段**：文档中出现的完整代码。
- **内联代码**：正文中的参数、表达式或代码。

### 规则

- **规则1** 代码片段、内联代码来源于产品，必须与实际代码保持一致。
- **规则2** 代码片段显示符合代码缩进要求。
- **规则3** 代码片段关键参数需要进行解释，可以使用代码注释或增加表格等方式进行说明。
- **规则4** 代码片段中的关键代码段用粗体突出显示。
- **规则5** 使用内联代码标识正文中的参数、表达式或代码。
- **规则6** 使用代码片段标识文档中出现的完整代码，与正文分开。
- **规则7** 使用代码片段、内联代码严禁包含敏感信息，对外发布之前必须经过 CodeCC/CodeDog 代码敏感信息扫描。

### 建议

- **建议1** 完整举例中的代码可执行。
- **建议2** 代码尽量有相应的注释。
- **建议3** 当需要对代码添加注释时，被注释的代码后紧跟注释内容。

## 二、链接规范

### 注意事项

- 链接必须可访问，发布前后需检查，避免出现404问题。
- 外网链接不得使用相对链接，必须使用绝对链接。
- 官网文档不得使用内部预览链接（带!preview或 !editLang），因为预览链接用于内部人员预览，严禁对外开放。

### 写作要求

- 链接必须带名称（title），不能直接贴网址。如果没有名称（title），不会显示为链接。
- 链接名称（title）长度要适度，描述要准确。
- 官网文档中链接默认为新标签页打开，如果不是，请联系开发人员修复。
- 相对链接如果是带/doc/product/，建议修改为/document/product/对应链接。

## 三、举例规范

### 规则

- **规则1** 所有举例统一放到"例如"后面。

正例：自定义云服务器名称（例如 WordPress），单击**确定**保存。
反例：修改为 "WordPress"（可以自定义），单击**确定**保存。

- **规则2** 举例需符合用户习惯。

### 建议

- **建议1** 描述参数取值时，建议提供示例，以降低用户理解成本。
- **建议2** 举例使用"例如"，不用"比如"。

标点符号使用：
  - 如果"例如"后面是短语，则"例如"与短语之间不加逗号。
  - 如果"例如"后面是句子，则"例如"与句子之间加逗号。

- **建议3** IP 地址示例建议使用私有 IP 地址；若需使用公有 IP 地址，请不要使用实际环境的 IP 地址，避免信息泄漏。

> **说明**：
> 私有 IP 地址属于非注册地址，专门为组织机构内部使用。
> RFC1918 定义了 IPv4 私有 IP 地址范围如下：
> - A：10.0.0.0~10.255.255.255，即10.0.0.0/8
> - B：172.16.0.0~172.31.255.255，即172.16.0.0/12
> - C：192.168.0.0~192.168.255.255，即192.168.0.0/16
> RFC 4193 定义了 IPv6 的私有 IP 地址范围：FEC0:0000:0000:0000:0000:0000:0000:0000/10

- **建议4** 域名举例建议使用 example.com，避免使用已经被注册域名。

> **说明**：example.com及对应的 org/net 域名，都是保留的二级域名（根据RFC 2606，第3部分），用于在文档中举例使用。该类域名不能被注册使用。

### 参考标准

- RFC 1918
- RFC 4193
- RFC 2606

## 四、步骤规范

### 规则

- **规则1** 步骤需要经过验证，能执行。
- **规则2** 步骤要详尽，需交代必要的操作场景。特别需要交代清楚什么用户在哪里执行操作。
- **规则3** 动作和描述分开。描述、操作结果另起一段。
- **规则4** 步骤操作后，需要提供操作结果。例如执行命令，需提供执行后显示信息。
- **规则5** 步骤中有复杂界面操作或对应界面控件较隐秘时，需在下方增加图示。图示信息需要与步骤保持一致。
- **规则6** 步骤中需要使用到工具等资源，需要就近提供对应官方下载链接。
- **规则7** 步骤描述过程中不要混杂小段说明性文字，应该在步骤结束后添加必要的说明。

> **说明**：说明性文字可以使用"说明"或"注意"样式，具体请参见说明与注意规范。

- **规则8** 所有步骤操作完成后，需要有方法去检查或验证操作是否已成功。例如，界面提示成功。

### 建议

- **建议1** 提供步骤的执行所需时间。
- **建议2** 通常情况下，一个过程中的步骤不超过9个。
- **建议3** 如果步骤可以跳过，需要进行说明，并提供下一个步骤的链接。
- **建议4** 如果步骤复杂，同时有其他文章进行具体描述，可以进行引用，不展开描述，提供对应链接即可。内容引用的相关写作规范，请参见内容引用规范。
- **建议5** 步骤作为文章标题时，使用"步骤+阿拉伯数字：具体描述"。

举例：步骤1：配置云端设备对象

## 五、表格规范

### 规则

- **规则1** 表格至少为2行2列。
- **规则2** 表格设计简洁，相同类型表格，风格需要保持一致。
- **规则3** 表格应提供表头，词汇表除外。
- **规则4** 表头设计简洁，相同类型表格的表头，风格需要保持一致。

> **说明**：同样对参数进行说明的表，不应出现"参数说明"、"参数解释"、"参数含义"、"参数意义"等不同的表头内容，需要全文保持统一。

- **规则5** 在同一个表格中，不允许间隔出现2行表头。
- **规则6** 同一列信息的表达方式一致，结尾的标点符号要保持一致。即统一使用句号结尾，或统一不使用句号结尾。

> **说明**：
> - 如果表格一列全是句子或同时存在句子和片段（单词、短语），建议采用句末标点。
> - 如果表格一列全部为片段（单词、短语），建议句末不使用标点。

- **规则7** 不出现空白的单元格，无内容单元填写"无"或特定含义符号"-"。

> **说明**：若使用特定含义符号，需说明符号代表的意义。

- **规则8** 如果多个单元格中的内容相同，将内容复制或者采用多个单元格合并的方式，不得使用"同上"或"同下"。
- **规则9** 在同一个单元格中，数值和单位要在同一行，不要换行。

### 建议

- **建议1** 表格行数≤9行，列数≤4列。以2～3列为佳。
- **建议2** 表格应提供表说明，且说明简明扼要，长度不能超过表的宽度。

## 六、图形规范

### 注意事项

- 禁止使用图片来呈现表格。
- 禁止使用背景透明的位图图标。
- 图中所有的图标风格保持一致。
- 杜绝使用非授权软件或来历不明的软件的界面。
- 使用中国地图时，必须使用国家正规、完整的地图，具体要求请参见《港澳台地域文案的指引》。
- 含[开始>程序]菜单项的界面有知识产权隐患。禁止截取含开始 > 程序菜单项的界面，其路径尽量用语言描述。
- 敏感信息需要打码，例如个人账户、姓名、真实的 SecretId、SecretKey、实例ID、节点名、IP 等。

> **打码建议**：建议只打码部分字段，如中间部分或中尾部。

### 基本要求

- 图文信息一致，高度契合。
- 截图时，只截取有效的信息。例如，截取控制台图片时尽量避免截取左侧目录。
- 截图时，要求当前窗口是激活的，非必要时不能出现鼠标或光标。
- 图形中需避免出现大段文字，描述性语言建议放到图外，用编号替代。
- 图形中包含缩略语时，需要在图外用文字对缩略语进行解释说明。
- 绘制的图形中的文字字体需公司有相应版权，同时用途为"全平台使用"，不能压图或压线。
- 同一组阿拉伯数字应在同一行，不能跨两行。
- 图片大小978px为宜。
- 小图标大小20×20px为宜。
- 图中文字和图案要清晰，不能有重影。
- 同一篇文档中图比例尺尽量保持一致，不要有边框。
- 同一篇文档有多个图形时，图形之间需要有描述图形的正文文字。
- 图片不得存储在外部网站，请使用野鹤文章编辑器上传图片。

内部允许的图片域名：
- mc.qcloudimg.com
- main.qcloudimg.com
- mccdn.qcloud.com（避免使用，研发不再维护，需要重新上传）
- -qcloudimg.tencent-cloud.cn

> **说明**：文档页面上图片默认提供放大功能，单击即可放大。若有特殊需求，可以在img标记对配上`data-nonescope="true"`识别属性，即可关闭放大功能。

### 设计规范分类

- 界面截图规范
- 拓扑图设计规范
- 流程图设计规范
- 场景图设计规范
- 其他图形设计规范

## 七、视频规范

产品文档目前仅支持嵌入腾讯产业互联网学堂视频。视频URL需要满足如下条件：
- 课程地址需要为 `https://cloud.tencent.com/edu/learning/quick-play`。
- 视频卡片（弹框播放）：不要带 `&withPoster=1&notip=1` 参数，需要带 `&auto=1` 参数。
- 视频模块（页面播放）：需要带 `&withPoster=1&notip=1` 参数，不要带 `&auto=1` 参数。

### 规则

- **规则1** 不得插入与文档主题不匹配的视频。
- **规则2** 视频有价值，讲解内容正确，符合逻辑，知识点解释严谨，不夸大功能。
- **规则3** 视频不得涉及政治局势、宗教信仰、国际关系、国家利益等话题，避免提及友商。
- **规则4** 视频中不得出现错别字、敏感词、法规禁词等。
- **规则5** 视频内容完整，画面无水印。
- **规则6** 视频需清晰，配音与视频同步，播放流畅，不卡顿。
- **规则7** 视频中出现的元素（如图片、商标）应确保有相应版权，避免版权纠纷。
- **规则8** 视频中敏感信息需打马赛克。
- **规则9** 视频中不出现无关信息，例如浏览器不能出现收藏的无关网址、收藏夹、默认搜索引擎、无关插件、广告等。
- **规则10** 视频不出现背景环境噪音，例如手机铃声、汽车鸣笛、键盘/鼠标点击声等。
- **规则11** 配音清晰，使用标准普通话，避免方言。
- **规则12** 配音音量大小适中，不得出现破音、喷麦、电流音、麦克风杂音等。

### 建议

- **建议1** 视频需要全屏录制，避免出现黑框。
- **建议2** 视频码率最低1800kbps（推荐2400kbps），音频码率最低192kbps（推荐320kbps），视频帧率30fps或以上。
- **建议3** 视频格式建议使用标准 MP4格式（H.264视频编码+AAC 音频编码）。
- **建议4** 配音语速适中，建议每分钟180-250字。
- **建议5** 配音避免频繁的习惯性用语和语气词，例如然后、嗯、咱们等。
- **建议6** 配音无长时间停顿，中间无口误或描述错误，避免重复说话。

## 八、界面控件规范

### 规则

- **规则1** 文档中引用界面控件名称时，**加粗**，以便识别。

举例：在云服务器选项卡中，单击**新建**。

- **规则2** 不在按钮标签后再增加"按钮"。

正例：单击**新建**。
反例：单击**新建**按钮。

- **规则3** 对于连续界面操作，使用"选择一级菜单 > 二级菜单 > 三级菜单"来描述，" > "前后要加空格。

举例：登录管理控制台，选择**自助解封** > **解封操作**，找到状态为自动解封中的防护 IP，单击操作列中的**解封**。

- **规则4** 当界面控件非常多时，需要给出方位的指示，让用户能快速定位到所指示的控件。

举例：界面左上方、右上方、中间、左下角、右下角等。

- **规则5** 描述按钮和菜单时，不要加上快捷键和加速键标识。

正例：单击**新建**
反例：单击**新建（C）**

- **规则6** 表示按键时，与键盘上显示的名称保持一致。

举例：按 Enter 键

- **规则7** 小图标需要截图，使用"单击XXX"。小图标的大小，请参考图形规范。
- **规则8** 描述信息应与界面控件一致，高度契合。

> **说明**：根据《标点符号用法》（GB/T 15834―2011）的4.9.1条款，以及4.9.3.2条款和4.9.3.5条款，方头括号"【】"用法是注释内容、补充说明作用，一般用于报刊标示电讯、报道的开头等，作为界面控件使用不是很合适，因此采用业界通用做法（**加粗形式**）来代替方头括号"【】"使用。

## 九、项目列表规范

项目列表，即 Item list，包括有序列表和无序列表。

### 规则

- **规则1** 当项目列表项是词汇、短语时，统一不加标点符号。
- **规则2** 当项目列表项是句子时，统一加句号。
- **规则3** 当需要对项目列表项进行说明时，说明内容要使用缩进。
- **规则4** 一个项目列表的列表项≥2项。
- **规则5** 项目列表的嵌套≤1层。

正例（嵌套1层）：
- 列表项
  - 列表项
  - 列表项
- 列表项

反例（嵌套2层）：
- 列表项
  - 列表项
    - 列表项（❌ 嵌套过深）

### 建议

- **建议1** 列表项采用相似结构，例如，全部采用短语或句子。
- **建议2** 特殊情况下，如果不能避免出现短语和句子混合的情况，统一加句号。
- **建议3** 一个项目列表的列表项≤9项。
- **建议4** 描述要方式一致。
  - 采用统一的句式。例如，统一省略主语，采用动词＋宾语的句式。
  - 采用相同的语气，例如，统一使用陈述句，避免有的是疑问句，有的是陈述句。

## 十、内容引用规范

### 规则

- **规则1** 内容引用统一表达为"请参见"。
- **规则2** 被引用的内容需要配置超链接，方便用户查找。

举例：用户签名的生成方法请参见 [生成签名](URL)。

- **规则3** 被引用的内容有标题的，则将标题作为超链接的title；被引用的内容没有标题的，则使用短语进行概括，短语作为超链接的title。
- **规则4** 针对无法穷举的内容，宜采用引用。

举例：更多规格型号，可通过 [XXX平台](URL) 进行查询。

### 建议

- **建议1** 针对被引用的内容较少（少于50个字），但必须说明的情况，建议重新描述一遍，不使用引用。
- **建议2** 针对被引用的内容较多，不利于重新描述的情况，可以采用引用。
- **建议3** 如果内容与被引用的内容在同一篇文档，且两者相隔较近，不建议配置超链接。

## 十一、说明与注意规范

### 说明使用规则

**用途**：表示是正文的附加信息，是对正文的强调和补充。例如，提供给用户的一些容易忽视的小功能、技巧，这些小功能或技巧能够为用户带来便利；或者通过简短的例子对操作中的任务进行补充说明，增进用户对任务的理解。

### 注意使用规则

**用途**：表示有低度的潜在风险，主要是用户必读或较关键信息，若用户忽略注意消息，可能会因误操作而带来一定的不良后果或者无法成功操作。一般来说，解决产生的问题比较麻烦。

### 警告使用规则

**用途**：表示有中度的潜在风险，例如用户应注意的高危操作，如果忽视这些文本，可能导致设备损坏、数据丢失、设备性能降低或不可预知的结果。

### 禁止使用规则

**用途**：表示有高度潜在危险，例如用户应注意的禁用操作，如果不能避免，会导致系统崩溃、数据丢失且无法修复等严重问题。

### 建议

- **建议1** 同一篇文档不建议超过3个以上的禁止、警告、注意或说明。如果需要有3条以上事项，建议新增二级标题"注意事项"，再对各条事项进行罗列。
- **建议2** 同一篇文档有多个禁止、警告、注意或说明时，需要有正文文字或表格等其他元素进行间隔。
- **建议3** 禁止、警告、注意、说明的内容不宜过长，建议不超过6行。
