# 腾讯云文档类型写作规范

> 来源：腾讯云产品文档写作规范体系 TAPD Wiki 官方规范（描述类文档写作规范、操作类文档写作规范、参数类文档写作规范、故障类文档写作规范、常见问题写作规范、词汇表写作规范、法律法规类相关建议）

## 一、文档类型分类体系

腾讯云产品文档按内容类型分为以下大类：

| 大类 | 包含文档类型 | 核心特征 |
|------|-----------|---------|
| **描述类** | 产品简介、功能介绍、计费说明、概念解释、产品优势、应用场景 | 向用户解释"是什么""为什么" |
| **操作类** | 快速入门、操作指南、购买指南、最佳实践、运维指南、安装指南 | 指导用户"怎么做" |
| **参数类** | API 文档、配置参数说明、SDK 文档、规格参数 | 提供精确的参数/接口定义 |
| **故障类** | 故障排查、故障处理、错误码说明、问题诊断 | 帮助用户"出了问题怎么办" |
| **FAQ 类** | 常见问题 | 以问答形式解决用户疑问 |
| **词汇表类** | 术语表、词汇表 | 定义产品领域的专有术语 |
| **公告类** | 产品公告、服务公告、变更通知 | 传达产品变更和重要通知 |
| **联系类** | 联系我们 | 提供获取帮助和支持的渠道 |
| **协议类** | 服务等级协议（SLA）、服务条款 | 定义服务承诺和法律条款 |
| **法律法规类** | 合规建议、敏感词汇过滤、港澳台地域文案指引 | 法律法规合规相关内容 |

## 二、描述类文档写作规范

### 文档用途

描述类文档向用户介绍产品定义、功能、架构原理等，例如《产品简介》。

### 标题要求

- 标题概括反映章节的中心内容。
- 标题尽量简洁扼要，涵义确切。
- 标题采用**名词性词组**的结构，例如"云服务器概述"。
- 同一级标题建议用一种结构表达。
- 下级标题不重复上一级标题的内容。
- 标题中直接使用缩略语，不需要全称。
- 标题中不能带上下标。
- 禁止在标题中用"&"表示并列，要使用"和"或"与"。
- 禁止在标题中用"/"表示"与"和"或"的关系，要使用"与"、"或"。
- 禁止在标题中用连字符或短破折号表示补充说明，应使用冒号或圆括号表示。
- 标题尽量简洁，不引起歧义的情况下，去掉标题中不必要的词。
- 若完成一个操作可以使用多种方式，操作类标题中使用圆括号简要说明不同的方法。

### 写作思路

1. **它是什么（必选）**：讲解它的定义，最好是A是B这种句式。
2. **它的作用（必选）**：讲解它的功能，先概括性讲功能，再进行分点描述。
3. **它的结构（可选）**：讲解它的组成结构，例如分成哪些模块，每个模块定义，模块之间关系等。
4. **它的规格（可选）**：讲解它都有哪些规格型号，每一种型号的参数说明，应用场景等。
5. **它的限制（可选）**：讲解它的使用限制，例如，配额限制、区域限制等。
6. **其他方面（可选）**：讲解它的其他方面，例如与其他模块之间关系等。

### 描述类文档模板

```markdown
# [产品名称]简介

## 什么是[产品名称]

[产品名称]（[英文名称]，[缩写]）是腾讯云提供的[产品定位一句话描述]。
[核心价值和能力概述]。

## 产品功能

### [功能模块一]
[功能描述]

### [功能模块二]
[功能描述]

## 产品优势

- **[优势一]**：[具体说明]
- **[优势二]**：[具体说明]

## 应用场景

### [场景一名称]
[场景描述 + 产品如何解决该场景需求]

## 使用限制

[配额限制、区域限制等]

## 基本概念

| 概念 | 说明 |
|------|------|
| [概念 A] | [定义说明] |
| [概念 B] | [定义说明] |
```

## 三、操作类文档写作规范

### 文档用途

操作类文档用于指导用户完成任务，例如《操作指南》、《运维指南》、《安装指南》等。

### 写作要求

#### 一、标题（必选）

- 标题概括反映章节的中心内容。
- 标题尽量简洁扼要，涵义确切。
- 标题需基于用户操作任务，采用**"动词＋主题词"结构**，例如"连接数据库"。
- 标题长度不得超过 **15 个中文字符**。
- 同一级标题建议用一种结构表达。
- 下级标题不重复上一级标题的内容。

#### 二、操作场景（必选）

操作场景从 **5W2H1E** 维度进行写作，其中 How much（多少）、Effect（效果/影响）为可选，其余为必选。

| 维度 | 说明 |
|------|------|
| What（什么） | 目的、内容 |
| Who（谁） | 操作人员 |
| Where（何处） | 实施地方 |
| When（何时） | 实施时间 |
| Why（为什么） | 原因 |
| How（如何） | 实施方法 |
| How much（多少）| 数量，主要是范围（可选） |
| Effect（效果/影响）| 实施的结果、效果，或造成影响（可选） |

#### 三、对系统影响（可选）

穷举该操作所有可能对系统造成的影响，例如导致业务暂停、数据无法写入等，方便用户提前预判风险。

#### 四、前提条件（可选）

穷举该操作所需的前提条件，例如注册账户、登录控制台等，让用户提前知道需要做哪些完成哪些条件才能操作。

#### 五、操作步骤（必选）

- Step by Step 描述操作步骤，指导用户完成任务，避免操作进入死胡同。
- 步骤要详尽，特别需要交代清楚以什么用户在哪里操作。
- 步骤需要经过验证，能执行。
- 命令或代码格式要正确，建议提供执行后显示信息。
- 动作和描述分开。描述、操作结果另起一段。
- 下载地址或提示信息在使用到的步骤体现。
- 注意过程步骤描述中不要混杂小段说明性文字，应该在一个过程（或者子过程）结束后添加必要的说明。
- 操作完成后，需要有方法去检查或验证操作是否已成功。例如界面提示等。

#### 六、相关操作（可选）

与该任务相关操作，可以是同类型操作，也可以是接下来会进行的操作。如果操作有前后关系，需要进行排序。

#### 七、附录（可选）

补充说明信息，如语法说明、参数表等等。

### 操作类文档模板

```markdown
# [操作名称]

## 操作场景

[说明在什么场景下需要执行此操作，按 5W2H1E 维度]

## 对系统影响（可选）

[穷举该操作所有可能对系统造成的影响]

## 前提条件（可选）

- 已 [前置操作一]，详情请参见 [链接]。
- 已获取 [必要权限/资源]。

## 操作步骤

1. 登录 [产品名称控制台](URL)。
2. 在左侧导航栏，选择**[菜单名称]**。
3. 在[页面名称]，单击**[按钮名称]**。
4. 在弹出的对话框中，配置以下参数：
   | 参数 | 说明 |
   |------|------|
   | **[参数 A]** | [参数说明和取值范围] |
   | **[参数 B]** | [参数说明和取值范围] |
5. 单击**确定**。

操作完成后，[预期结果描述]。

## 相关操作（可选）

- [相关操作一](链接)
- [相关操作二](链接)

## 附录（可选）

[补充说明信息]
```

## 四、参数类文档写作规范

### 文档用途

- 在市场阶段，负责技术决策的用户看参数类文档，了解功能实现的原理，考察易用性。
- 在选型阶段，负责应用的用户看参数类文档，确定参数设置的范围和取值。
- 在测试阶段，负责验收的用户看参数类文档，核对功能实现的完成情况。
- 在操作与维护阶段，负责操作的用户看参数类文档，优化软件性能。

### 标题要求

- 标题概括反映章节的中心内容。
- 标题尽量简洁扼要，涵义确切。
- 标题采用**名词词组结构**，例如"规格参数"。
- 禁止在标题中用"&"表示并列，要使用"和"或"与"。
- 禁止在标题中用"/"表示"与"和"或"的关系，要使用"与"、"或"。
- 标题长度不得超过 **15 个中文字符**。
- 同一级标题建议用一种结构表达。
- 下级标题不重复上一级标题的内容。

### 表格参数说明

| 字段 | 说明 |
|------|------|
| 名称 | 填写参数名称，例如 Region |
| 含义 | 填写参数定义，例如地域 |
| 类型 | 参数的数据类型，例如 String |
| 必填 | 填写是或否，如果该参数是必选参数，则填是，反之为否 |
| 取值范围 | 参数的取值范围，例如 ap-bangkok、ap-beijing 等，有默认值需要写明默认值 |
| 备注 | 补充参数的信息，有则填写，无则写"-"。例如说明该参数与某参数关联使用、该参数仅在某场景使用、生效条件等 |

### 参数类文档模板

```markdown
# [参数文档标题]

## 概述

[简要说明参数文档的用途和适用场景]

## 参数说明

| 名称 | 含义 | 类型 | 必填 | 取值范围 | 备注 |
|------|------|------|------|---------|------|
| Region | 地域 | String | 是 | ap-bangkok、ap-beijing 等 | - |
| [参数名] | [定义] | [类型] | [是/否] | [取值范围，含默认值] | [备注或"-"] |
```

## 五、故障类文档写作规范

### 简介

本规范旨在给所有从事或参与腾讯云文档写作工作的人员，提供统一的《故障处理》写作规范与模板。

一般情况下，《故障处理》包括如下内容：
1. 现象描述
2. 可能原因
3. 解决思路
4. 处理步骤

### 一、标题

- **规则1** 标题必须包含故障现象。

举例：无法登录云服务器

- **规则2** 标题尽量简洁，不引起歧义的情况下，去掉标题中不必要的词。

正例：CPU 使用率过高（Windows 系统）
反例：CPU 使用率过高排查（Windows 系统）

### 二、现象描述

**主要内容**：描述故障发生的背景、故障现象（包括不限于错误码、提示信息等）。

**写作关键点**：
- 内容根据3W（what/where/when）描述清楚。
- 故障相关信息需要描述具体、清晰。

### 三、可能原因

**主要内容**：描述故障可能原因。

**写作关键点**：
- 可能原因有多少个列多少个。
- 同一类型的原因需要进行归类。

### 四、解决思路

**主要内容**：精简描述故障处理的整体思路或方法，让用户了解故障处理的逻辑。

**写作关键点**：
- 内容精简。
- 逻辑或过程操作复杂的建议使用流程图。

### 五、处理步骤

**主要内容**：Step by Step描述故障处理的步骤，指导用户处理故障，避免操作进入死胡同。

**写作关键点**：
- 步骤要详尽，特别需要交代清楚以什么用户在哪里操作。
- 步骤需要经过验证，能执行。
- 命令或代码格式要正确，建议提供执行后显示信息。
- 动作和描述分开。描述、操作结果另起一段。
- 下载地址或提示信息在使用到的步骤体现。
- 注意过程步骤描述中不要混杂小段说明性文字，应该在一个过程（或者子过程）结束后添加必要的说明。

### 故障类文档模板

```markdown
# [故障现象标题]

## 现象描述

[描述故障发生的背景、故障现象，包括错误码、提示信息等]

## 可能原因

- [原因一]
- [原因二]
- [原因三]

## 解决思路

[精简描述故障处理的整体思路或方法]

## 处理步骤

1. 登录云服务器，执行以下命令，[操作目的]。
   ```
   [命令]
   ```
   [执行后预期输出]

2. [下一步操作]。

3. [验证操作是否成功]。
```

### 故障类文档示例

```markdown
# 域名无法解析（CentOS 6.x 系统）

## 现象描述

对操作系统为 CentOS 6.x 的云服务器，进行重启或者执行命令 `service network restart` 之后，云服务器无法解析域名。同时，查看配置文件 `/etc/resolv.conf`，发现 DNS 信息被清空。

## 可能原因

在 CentOS 6.x 操作系统中，因为 grep 版本的不同，initscripts 的版本低于9.03.49-1存在缺陷。

## 解决思路

升级 initscripts 到最新的版本，并重新生成 DNS 信息。

## 处理步骤

1. 登录云服务器，执行以下命令，查看 initscripts 的版本情况确认是否存在该问题。
   ```
   rpm -q initscripts
   ```
   如显示 `initscripts-9.03.40-2` 低于存在的问题版本 `initscripts-9.03.49-1`，存在 DNS 被清空的风险。

2. 执行以下命令，将 initscripts 升级到最新的版本，并重新生成 DNS 信息。
   ```
   cat /dev/null > /etc/resolv.conf
   service network restart
   yum makecache
   yum -y update initscripts
   ```

3. 升级完成后，执行以下命令，检查 initscripts 的版本信息，确认升级是否成功。
   ```
   rpm -q initscripts
   ```
   显示的版本不同于之前版本，且高于 `initscripts-9.03.49-1`，操作升级成功。
```

## 六、常见问题写作规范

### 简介

常见问题（Frequently Asked Questions，简称FAQ），指用户常问到的一些问题和解答，可以理解为一系列的 Questions and Answers (Q&A)。

### 规则

- **规则1** 问题必须明确，简单明了。
- **规则2** 问题使用疑问句式表达，结尾用问号。
- **规则3** 回答必须直接恰当，不能答非所问。
- **规则4** 单个产品的常见问题≥5个。
- **规则5** 问题分类要在同一维度，描述方式要一致。

### 建议

- **建议1** 同一级问题分类≤9项，父类可以再分子类。
- **建议2** 故障处理相关问题建议引用故障类文档，具体请参见故障类文档写作规范。
- **建议3** 尽量一个问答解决一个问题，相关问题就近展示。

### 样式

- **问题**：三级标题，疑问句式（以问号结尾）。
- **回答**：正文格式。
- **TOC**：文档篇幅未超过2屏，则关闭TOC；文档篇幅超过2屏，则开启TOC。

### 常见问题模板

```markdown
# 常见问题

## [分类一名称]

### [问题一]？
[直接给出答案]

### [问题二]？
[直接给出答案]

## [分类二名称]

### [问题三]？
[直接给出答案]
```

## 七、词汇表写作规范

### 简介

- **定义**：词汇用于描述、定义某一领域的知识。
- **解释原则**：立足于帮助用户快速和方便地理解产品特性，解决用户认知问题。
- **选择原则**：只选择必需的词汇，建议选择产品常用概念、特性相关概念、行业中与产品强相关概念。

### 词汇类型

一般情况，词汇包含如下分类：
1. 常见词汇用来表达熟悉概念
2. 常见词汇用来表达陌生概念
3. 陌生词汇用来表达熟悉概念
4. 陌生词汇用来表达陌生概念

### 规则

- **规则1** 词汇的定义必须遵守语法规则。
- **规则2** 词汇必须符合业界标准或者遵循公认的规范。
- **规则3** 使用常用词汇来表达熟悉概念时，不能对常用词汇进行定义。

> **说明**：当您使用常见词汇来表达用户熟悉的概念时，不必也不应该对这些概念进行定义。因为这样的定义无助于用户理解，反而使得词汇堆砌，影响用户抓住关键、核心的词汇。

- **规则4** 使用常用词汇来表达陌生概念时，需要对常用词汇进行定义。

> **说明**：一些日常用词在某个领域具有特殊含义。这种含义与用户通常的理解有很大不同，这时就需要定义这个概念。当确认用户能够对这类词汇充分理解，也可省略定义。

- **规则5** 当需要用精确、方便的陌生词汇用来表达熟悉概念，同时需要定义或解释陌生的词汇。

> **说明**：所谓"陌生词汇表达熟悉概念"指有时需要用精确、方便，但比较生僻的词汇来表达熟悉的概念。这个陌生的词汇需要给出定义或解释，并确保定义或解释这类概念的词汇、语句是容易被理解的。

- **规则6** 使用陌生词汇用来表达陌生概念，同时需要定义或解释陌生的词汇。

> **说明**：技术文档中多数词汇归为这一类。用户陌生的词汇用来描述某个具体产品或某种技术，因此需要对这类概念进行定义、解释，以帮助用户理解。

- **规则7** 不使用多个词汇来指同一个概念。

> **说明**：需要做到一个概念对应一个词汇，至少是在同一本手册或者同一个产品中。

### 建议

- **建议1** 用简单明了的句子来定义词汇，以方便用户正确理解该词汇的含义。在定义时，可以把被定义的对象放入一个类别，以比较其与其他同类对象的不同之处。
- **建议2** 如果某个词汇适用于多个产品，则作一般定义，不可针对某个产品定义。
- **建议3** 先定义子概念，再定义整个大概念。把某个大概念分成若干子概念进行定义，先让用户明白具体的小概念，再掌握整个大概念。
- **建议4** 标明某个被定义的概念与用户所熟悉的概念的异同点。
- **建议5** 在定义一个词汇时，将该词汇的同义词写出来，而该同义词应是用户熟悉的，不能用更复杂、陌生的词汇来定义词汇。
- **建议6** 必要时，进一步指出词汇的起源。
- **建议7** 词汇的定义文字中还包括专业词汇，则需要另行解释。
- **建议8** 使用一般或非技术词汇时，与常用字典中的定义保持一致。
- **建议9** 重要词汇应该在正文中给予解释。重要词汇是指新技术词汇、不常见的技术词汇。
- **建议10** 在定义某个词汇时，不重复引用该词汇或者该词汇的变体。
- **建议11** 在定义某个词汇时，可以使用举例来扩展说明。
- **建议12** 如果词汇较多，宜按词汇首字母拼音或字母顺序进行排列。如果词汇间存在从属、因果等逻辑关系，也可按概念层级或逻辑关系进行排列。

### 词汇表模板

```markdown
# 词汇表

| 术语 | 英文 | 说明 |
|------|------|------|
| [术语 A] | [English Term] | [定义说明] |
| [术语 B] | [English Term] | [定义说明] |
```

## 八、法律法规类相关建议

### 基本原则

- 涉及法律法规合规内容时，需参考以下两份指引文档：
  - **《腾讯云官网相关敏感词汇过滤合规建议》**
  - **《港澳台地域文案的指引》**
- 涉及用户数据处理、隐私政策、合规要求的内容，需经法务审核。
- 技术文档中不对法律条款进行解释或承诺。
- 引用法规条文使用准确的名称和条款编号。
- 避免使用法律法规严禁词汇（广告法相关敏感词汇）。
- 避免使用宗教、政治导向词语。
- 关于港澳台的描述方法，必须参见《港澳台地域文案的指引》。

### 表述建议

- 使用"根据[法规名称]"引述法律依据。
- 不使用"承诺""保证"等法律责任性表述。
- 以"建议用户参考"替代"用户必须遵守"。

## 九、产品公告写作规范

### 文档用途

产品公告用于向用户传达产品变更、功能更新、维护通知、下线通知等重要信息。

### 标题要求

- 标题格式：`【产品名称】【发布日期】 公告主题`
- 示例：【数据传输服务】【2025年08月22日】 部分接口鉴权升级公告
- 公告主题应简洁明了，一句话说明核心变更内容。

### 写作要求

1. **背景说明**：说明公告的背景和原因。
2. **变更内容**：清晰列出具体的变更项。
3. **影响范围**：说明哪些用户、哪些地域、哪些功能受影响。
4. **用户操作**：告知用户是否需要采取操作，以及具体操作方式。
5. **生效时间**：明确变更的生效日期和时间。
6. **联系方式**：提供用户反馈渠道。

### 产品公告模板

```markdown
# [产品名称]产品公告

以下为[产品名称]的近期公告，请您关注。更多公告，请参见服务公告。

## [公告标题]

**发布日期**：[YYYY-MM-DD]

[公告正文：背景说明 → 变更内容 → 影响范围 → 用户操作 → 生效时间]
```

## 十一、服务等级协议（SLA）写作规范

### 文档用途

服务等级协议（SLA）定义了腾讯云产品的服务可用性承诺和赔偿方案，是用户选择和评估云服务的重要参考。

### 写作要求

- SLA 内容必须经法务审核后方可发布。
- 服务可用性计算公式必须清晰准确。
- 赔偿标准必须量化，不使用模糊表述。
- 免责条款必须穷举。
- 根据产品是否收费选择对应模板（收费产品/免费产品）。

### 标准结构

| 章节 | 是否必选 | 说明 |
|------|---------|------|
| 服务内容 | 必选 | 描述产品服务范围 |
| 服务可用性 | 必选 | 定义可用性计算方式和标准 |
| 赔偿方案 | 收费产品必选 | 赔偿标准和申请方式 |
| 免责条款 | 必选 | 不承担赔偿责任的情形 |
| 其他 | 必选 | 协议修改权和生效日期 |

### 注意事项

- 已上线产品的服务协议变更/上线，需提前周知客户。
- SLA 审批需按公司规定流程执行。

## 十二、服务条款写作规范

### 文档用途

服务条款定义了用户使用腾讯云产品时的权利和义务，是产品的法律合规文档。

### 写作要求

- 服务条款分为必要条款、可选条款和产品自定义条款。
- 必要条款所有产品均通用，不可省略。
- 可选条款由产品根据实际情况自行选取。
- 产品自定义条款由产品根据特殊需求自行增补。
- 最终内容必须经接口法务审核定稿。

### 条款分类

| 条款类型 | 说明 | 示例 |
|---------|------|------|
| **必要条款** | 所有产品通用 | 服务内容、服务费用、使用规范、数据保护、知识产权、保密、违约责任、争议解决、附则 |
| **可选条款** | 产品自行选取 | 服务保障、服务变更与终止 |
| **自定义条款** | 产品自行增补 | 根据产品特殊需求定义 |

### 注意事项

- 产品侧需结合自身特点填写和扩充条款内容。
- 已上线产品的服务协议变更/上线，需提前周知客户。
